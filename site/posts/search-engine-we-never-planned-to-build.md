Nobody wakes up and decides to compete with search APIs. We did not either. This is how Joule ended up with its own search engine anyway, why cost forced the decision, what it costs to run, and how an internal fix became a product we now offer over an API.

## The starting point

Joule's agents need web context. This is not optional. An agent answering a real question, drafting a real document, or executing a real workflow has to know what is on the web right now, not what a model memorized during training. Without retrieval, an agent is a very articulate liability.

The obvious solution was a search engine API. Clean integration, someone else's infrastructure, someone else's crawling problem, pay per query. Industry standard. So that is exactly what we did, and for a while it was the right call. When you are validating a product, buying beats building on almost every axis. You want your engineering hours on the parts that differentiate you, not on rebuilding commodity infrastructure.

## Where it broke

It worked. Then usage grew, and the flaw in the model showed itself.

The problem with pay-per-query is that your costs scale linearly with your success. Every new user added queries. Every new agent added queries. And agents are hungrier than humans: a single workflow with a retry loop can fire dozens of searches for one task. Humans search a few times and stop. Agents search as many times as the workflow graph tells them to.

There is a second problem that shows up later: dependency. Your latency is their latency. Your uptime includes their downtime. Your roadmap quietly inherits their pricing decisions. For a feature, that is acceptable. For infrastructure sitting under every agent on the platform, it is a strategic weakness.

We looked at the numbers, projected the growth curve, and made the call: build our own index.

## The index, and the bar it has to clear

We did not try to index the whole web. That is the trap that kills these projects. Indexing the web is a billion-dollar problem, and pretending otherwise is how side quests become graveyards.

We built around a narrower observation. A small index answers a large share of real queries, because query distributions are heavily skewed and the pages that answer today's questions look a lot like the pages that answered yesterday's. The v1 target is ten million pages, curated and filtered for quality. Not a thin layer over everything.

The size is not the interesting decision. What happens when the index does not have the answer is.

We do not serve a bad result. Every query gets scored, and when the top result comes back under 0.35 the query goes out to a rented API instead. That is a confidence bar, not a quota. Nobody chose a percentage. We chose the score below which we would rather pay than answer badly, and the ratio of hits to misses is whatever that bar produces.

So the miss is not the failure path. It is the input to the crawler. Every query that scores under the bar lands in a miss log, and the frontier grows out of that log and a domain ranking rather than out of a plan. We do not sit in a room guessing what to crawl. Demand decides, and the index compounds along the paths real queries already took.

## Everything is stored as markdown

A search engine built for people stores pages so they can be rendered. Ours stores them so they can be read by something with no eyes.

Every page we crawl comes out the other side as compressed markdown. Not the original HTML, not a DOM. Readability finds the article, turndown converts it, and the navigation, the cookie banner, the three ad slots and the newsletter modal are gone before anything is written down. Pages that ship an empty shell and fill it in with JavaScript get rendered in a real browser first, then go through the same funnel.

That choice pays twice. A page kept as markdown costs a fraction of what the raw HTML costs to store, so growing the index stays cheap, and cheap is the entire economic argument. And the thing on the other end of a query is an agent, so the format it wants back is the format we already have. There is a retrieve endpoint sitting next to search for exactly that. Search answers which pages. Retrieve hands over the text.

The crawler holds at one request per second per domain, which is slow and not negotiable. Everything upstream of the index is a guest on someone else's server.

## The index is derived state

The corpus is the source of truth. Everything else is rebuildable.

The text index holds no document that does not exist in the corpus. The vector table holds nothing that cannot be recomputed from it. Neither is a place where something lives, which is why changing engines is a configuration change and not a migration. We run SQLite's own full-text index by default and switch to Manticore with an environment variable.

That property is worth more than any single engine choice. Owning a stack is not about how much of it you wrote. It is about which half you are able to delete.

## Why we did not go all in on vectors

Vector search is the default answer now, and on its own it is worse than the thing it replaced.

We measured ours. Lexical ranking alone gives p@5 of 0.608. Fusing the lexical and vector rank lists gives 0.700. Reciprocal rank fusion, k=60, two orderings in and one out.

The reason to keep the lexical half is the queries embeddings are bad at. An error string. A function name. A version number. A model identifier. Those are exact-match questions, and a nearest-neighbour search will happily return five documents about the right topic that contain none of them. An agent chasing an identifier does not want the neighbourhood. It wants the address.

Recency sits on top of relevance and never replaces it. We overfetch the relevance pool at eight times the result count and re-sort inside it, so a fresh page can beat an older one it was already close to, and cannot win on being new alone. Curation, the manual pins and excludes, is applied last and overrides everything above it.

Embedding a query has a hard ceiling of one and a half seconds. Past that we stop waiting and answer lexically. A hybrid search that hangs is worse than a lexical search that returns.

## What it cost to run

Two scars, and both have the same root. One process, one writer, one event loop.

We put the corpus in SQLite as rows. A 2.2GB corpus produced a 5.66GB write-ahead log, and reads began stalling behind it. The fix was to stop pretending a document is a row. The corpus moved to files, and the database went back to holding the things that need a transaction.

Our own dashboard froze search. The full-table aggregates behind it were running on the thread that serves queries, so a report nobody was waiting on could stall a query someone was. Those aggregates have their own worker thread now. It is the textbook single-threaded trap, and it does not announce itself while the corpus is small.

There is no Docker in the repository, no Kubernetes and no CI. It is bare Node processes across a private network. That keeps a deploy small enough to hold in my head. It also means nothing catches a mistake for me.

None of that is a design failure. It is the bill for owning the thing, and it is the part an architecture diagram never shows.

## From cost fix to product

The index kept improving as the agents evolved. Better coverage, better freshness, better relevance on the query patterns that actually occur.

At some point we looked at what we had built and realized it had crossed a line. It was no longer an internal cost optimization. It was a capability: a search and retrieval layer designed for agents, tuned by agent usage, with an economic structure that improves with scale instead of degrading.

So now we are offering it over an API, for anyone.

The pattern here is worth naming, because it repeats across the industry. We set out to remove a line item from our infrastructure bill. We ended up with a search product. Constraints did the product design for us. Some of the best components in any platform are the ones nobody planned, born from a bill that grew too fast.

## The lesson for builders

Buy first. Prove the product. But watch the cost curve of every external dependency sitting under your core loop, and know in advance which line, once crossed, means you build.

For us that line was the point where a query we could answer ourselves cost less than the same query rented. We crossed it, we built, and the accident became an asset.
